1. Objectives
▼
  • Verify that the Login feature functions correctly across all defined functional, validation, security, and usability requirements.
  • Verify that the New Test Case creation feature functions correctly across all defined functional, validation, and usability requirements.
  • Ensure frontend validation prevents unnecessary backend calls on both features.
  • Confirm security standards are upheld on the Login page (HTTPS, masked passwords).
  • Validate clear, accessible error messaging and usability across both features.
📋
2. Scope
▼

In Scope

  • Login page — all four requirement categories
  • New Test Case page — all three requirement categories
  • Frontend validation behaviour
  • Navigation flows and redirects
  • Error and success states
  • Form field usability
  • Security: HTTPS, masked input

Out of Scope

  • Backend authentication implementation
  • Password reset flow internals
  • Admin login page functionality
  • Test case execution / results
  • Performance & load testing
  • Accessibility audit (WCAG)
  • Cross-browser matrix testing
🔬
3. Test Approach
▼
  • Functional tests — black-box testing of all user-facing flows; executed manually first, then automated for regression.
  • Validation tests — boundary and negative testing of all required fields; confirm frontend prevents bad data before submission.
  • Security tests — manual inspection of HTTPS enforcement and password masking; no penetration testing in this cycle.
  • Usability tests — manual review of labels, placeholders, toggle visibility, and keyboard behaviour.
  • Regression scope — all P1 (High priority) test cases are candidates for automation and inclusion in the regression suite.
Automation candidates are marked with the Automated badge in the test case list below. Manual-only cases are marked Manual.
✅
4. Entry & Exit Criteria
▼

Entry Criteria

  • Feature implementation is code-complete
  • Build is deployed to test environment
  • Test environment is accessible over HTTPS
  • Valid and invalid test credentials are provisioned
  • Test data for New Test Case feature is available
  • This test plan is reviewed and approved

Exit Criteria

  • All High priority test cases pass
  • No open Critical or High severity defects
  • All security test cases pass without exception
  • Medium priority failures are documented with accepted risk
  • Test results are logged and signed off by QA lead
🖥
5. Test Environment
▼

Requirements

  • HTTPS-enabled test environment
  • Modern browser (Safari, Chrome, Firefox)
  • Test user accounts (valid + invalid credentials)
  • Admin account for admin link verification
  • Network access to trigger backend calls

Assumptions

  • Dashboard page exists and is accessible post-login
  • Forgot Password page route is implemented
  • Admin login page route is implemented
  • /login route is stable and accessible
  • Test case list page exists for back-navigation test

9. Defect Reporting
▼
  • Tool: Radar
  • Severity classification: Critical, High, Medium, Low aligned to test case priority.
  • Required fields per radar: Title, Steps to Reproduce, Expected Result, Actual Result, Build/Version, Environment, Attachments (screenshots or logs where applicable).
  • Security defects (LGN-S-*) must be filed immediately and escalated to the security team regardless of severity classification.
  • Re-test policy: All fixed defects must be re-tested by the original tester before closure.
Any defect related to HTTPS enforcement or password exposure must be treated as Critical severity and escalated immediately.
